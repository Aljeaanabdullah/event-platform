## الاستكشاف العام (Phase 5)

- `search_events(...)`: بحث بالاسم/الملخص/الوصف/المكان/اسم المنظّم (بالعربية والإنجليزية، `ILIKE` مع تهريب `%` و`_`)،
  فلاتر التصنيف والمحافظة والفترة والسعر والمميزة، ترتيب (`date|price_asc|price_desc|newest`)، وترقيم مع `total_count`.
- `get_event_details(slug)`: كل بيانات صفحة الفعالية (الصور، التذاكر مع المتاح، المنظّم، التصنيف) في JSON واحد.
- الدالتان `SECURITY DEFINER` للقراءة فقط، وتُرجعان **فقط** فعاليات `published` (والملغاة في صفحة التفاصيل) لجهات `approved`.
- `p_include_test`: تمرّره الواجهة `true` فقط عند `SHOW_TEST_DATA=1` وخارج Production.

## مبادئ الأمان

1. **لا صلاحيات افتراضية**: Supabase يمنح `anon` و `authenticated` كل الصلاحيات على أي جدول جديد افتراضيًا. ألغينا ذلك، وكل صلاحية ممنوحة صراحةً.
2. **صلاحيات على مستوى الأعمدة**: مثلًا المستخدم يعدّل اسمه وهاتفه فقط — لا يستطيع لمس `platform_role`. المنظّم يعدّل محتوى الفعالية — لا يستطيع لمس `status` أو `is_featured` أو عدادات التذاكر.
3. **RLS على كل الجداول**: تحدد الصفوف المرئية لكل مستخدم.
4. **العمليات الحساسة عبر دوال فقط**: الحجز، الدفع، النشر، المراجعة، الأدوار — كل دالة تتحقق من الصلاحية داخليًا، وكلها `SECURITY DEFINER` مع `search_path` فارغ.
5. **سجل تدقيق غير قابل للتعديل**: Trigger يمنع `UPDATE/DELETE/TRUNCATE` حتى على `service_role`.

## الحجز ومنع البيع الزائد

```
reserve_tickets  →  قفل صفوف أنواع التذاكر بترتيب ثابت (FOR UPDATE)
                 →  فحص المتاح = الإجمالي − المباع − المحجوز
                 →  إنشاء طلب pending_payment وحجز مؤقت (15 دقيقة)
confirm_order_payment (الخادم فقط)  →  مباع، إصدار تذكرة لكل وحدة، إشعار
release_expired_holds (pg_cron كل دقيقة)  →  تحرير الحجوزات المنتهية
```

- القيد `quantity_sold + quantity_reserved <= quantity_total` يمنع التجاوز حتى لو حدث خطأ في الكود.
- الأسعار والرسوم والعمولة تُحسب داخل قاعدة البيانات — لا يُقبل أي سعر من المتصفح.
- `confirm_order_payment` آمن للتكرار: نفس الدفعة مرتين = `already_paid`، دفعة ثانية مختلفة = `duplicate_payment` (تحتاج استرجاعًا)، دفعة بعد انتهاء الحجز ونفاد التذاكر = `needs_refund`.
- الطلبات المجانية تُؤكَّد فورًا بدون بوابة دفع.
- حد أقصى 3 طلبات معلّقة لكل مستخدم لمنع احتكار المخزون.

## رمز QR

- كل تذكرة لها `qr_token` عشوائي 256 بت. العمود **غير قابل للقراءة** لأي دور عبر الـ API.
- المالك يحصل عليه عبر `get_ticket_qr_token` فقط.
- `check_in_ticket` ذرّي: `UPDATE … WHERE status = 'valid'` — لا يمكن استخدام التذكرة مرتين.
- لغير المصرّح لهم تُرجع الدالة `invalid` دائمًا حتى لا تكشف وجود التذكرة.

> تعديل عن الخطة الأولى: كانت الخطة تخزين hash للرمز، لكن ذلك يمنع عرض QR للمالك لاحقًا.
> البديل المطبّق: الرمز مخزّن لكن محجوب تمامًا عن القراءة المباشرة، ويُعطى للمالك فقط عبر دالة.

## ملاحظات Supabase Advisors

- **"RLS بدون سياسات" على `rate_limits`**: مقصود — الجدول مغلق تمامًا ويُستخدم من الخادم فقط.
- **"دوال SECURITY DEFINER قابلة للاستدعاء"**: مقصود — هي العمليات التي يجب أن يستدعيها المستخدمون (الحجز، التحقق…)، وكل دالة تتحقق من الصلاحية داخليًا. الدوال الداخلية (`_finalize_order`, `log_audit`, `setting_int`) مغلقة تمامًا.
